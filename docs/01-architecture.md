# Насосолинго — архитектура приложения

Рабочая спека для масштабируемой обучающей игры для монтажников (iOS + Android), рынок РФ.
Версия 0.1 — черновик для обсуждения.

---

## 0. Развилка, от которой зависит всё

Прежде чем выбирать технологии, надо ответить на один вопрос:

**Это revenue-продукт или loyalty-инструмент?**

| | Loyalty-инструмент (рекомендую) | Revenue-продукт |
|---|---|---|
| Кто платит | Маркетинг Aquario | Пользователь (IAP) |
| Валюта в игре | Опыт → дилерская скидка, статус, сертификат | Опыт → рубли, платные жизни, подписка |
| Платёжный стек | **не нужен** | RuStore Pay + 54-ФЗ + фискализация + онлайн-касса |
| Метрика успеха | Лояльность канала, доля в спецификации, ↓ гарантийных | ARPU, LTV, конверсия в покупку |
| Сложность | Средняя | Высокая (+касса, +возвраты, +налоги) |

Судя по твоей дилерской стратегии (BRO, RRC, hero-card), это **loyalty-инструмент**: цель — вшить бренд в голову монтажника, привязать к дилерскому каналу и снизить брак монтажа. Тогда весь платёжный слой выпадает, и это огромное упрощение. Дальше документ исходит из этого сценария; места, где revenue-версия отличается, помечены `[IAP]`.

## 1. Российская специфика (определяет архитектуру)

Это не «фичи», это ограничения, которые надо заложить в фундамент.

**152-ФЗ — локализация персональных данных.** Телефон убрали, но PII остаётся: сертификат и скидка привязаны к реальному человеку, значит имя и регион собираются всё равно — это персональные данные гражданина РФ. По закону они должны храниться и обрабатываться в базах, физически расположенных в России. Следствие: основное хранилище PII — **российское облако** (Yandex Cloud / VK Cloud / Selectel / Cloud.ru), не AWS/GCP. Плюс нужно подать в Роскомнадзор уведомление об обработке ПД (оператор ПД). Отказ от телефона лишь уменьшает поверхность ПД, но не отменяет требование.

**Дистрибуция (пока только iOS).**
- **iOS:** App Store + TestFlight для беты. App Store работает; корпоративная программа Apple для РФ-компаний закрыта, но обычная публикация доступна. Нужен Apple Developer-аккаунт. Буфер 10–14 дней на модерацию.
- **Android — отложен.** Код на Flutter кроссплатформенный, поэтому Android-версия не потеряна: когда дойдёт до неё, канал — **RuStore** (ИП подходит), Google Play только для бесплатной раздачи. Пока не собираем и не публикуем.

**Авторизация: логин + пароль, без телефона.** Отпадает вся интеграция с flashcall/SMS. Взамен появляется парольная безопасность (см. раздел 4): хеширование Argon2id, защита от брутфорса, и — главное — выбор канала восстановления доступа.

**Пуш-уведомления: только APNs** (iOS). RuStore Push понадобится позже, вместе с Android. На бэкенде всё равно прячем за единым `NotificationService`, чтобы добавить второй канал без переделки.

**Аналитика:** данные не должны утекать за рубеж вместе с PII. **Yandex AppMetrica** (бесплатная, сильная, российская) для продуктовой аналитики + собственное хранилище событий для игровой экономики. Amplitude/Firebase — нежелательны.

**Платежи `[IAP]`:** только если revenue-версия. RuStore Pay: карты РФ-банков, СБП, оплата с баланса телефона, комиссия ~15%, встроенная фискализация под 54-ФЗ.

## 2. Технологический стек

Принцип: минимум движущихся частей, максимум совпадения с твоими текущими навыками (Python), никакого преждевременного усложнения.

### Клиент — **Flutter** (Dart)

Один кодовый база на iOS + Android. Почему не альтернативы:

- **не Unity** — это не аркада с физикой и 3D в реальном времени, а обучалка с анимированным UI, списками, формами, локализацией. Unity здесь даёт лишний вес, худшую работу с текстом/вводом и медленную итерацию. Unity оправдан, только если появится настоящий real-time геймплей (симулятор сборки системы в 3D — но это отдельный мини-модуль, не всё приложение).
- **не React Native** — можно, и у тебя есть JS-опыт, но для «игрового» плавного UI Flutter стабильнее по перформансу и анимациям.
- **не нативная разработка (Kotlin+Swift)** — двойная работа ради выигрыша, который тебе на этом этапе не нужен.

Flutter хорошо живёт в РФ, есть плагины под RuStore, flashcall-виджеты, RuStore Push. Для локального хранилища — **Drift** (SQLite) или Isar. Безопасное хранение токенов — `flutter_secure_storage` (Keychain/Keystore).

### Бэкенд — **Python / FastAPI**

Совпадает с твоим стеком (ozon-reports, n8n). На этом масштабе Python более чем достаточно.

**Критично:** начинать как **модульный монолит**, НЕ микросервисы. Один сервис с чёткими внутренними модулями (auth, content, economy, social, notifications). Микросервисы — это налог на сложность, который окупается только на большой команде и большом трафике. Выделять сервисы будешь потом, по факту боли, а не заранее.

Фоновые задачи (регенерация жизней по расписанию не нужна — считается на лету; но нужны: рассылка пушей, ротация лиг по неделям, отправка отчётов) — **Dramatiq** или **Celery** + Redis как брокер.

### Данные

- **PostgreSQL** — основное хранилище: пользователи, прогресс, экономика, сертификаты. Managed-инстанс в российском облаке.
- **Redis** — лидерборды (sorted sets — идеально ложатся на лиги и рейтинги потока), кэш, rate limiting (счётчики попыток входа), эфемерные токены сброса пароля.
- **Object Storage** (S3-совместимое: Yandex Object Storage / VK Cloud) — медиа уроков: картинки схем, **аудио для задания «послушай насос»**, контент-паки.
- **ClickHouse** — потом, для аналитики событий на масштабе (не на MVP).

### Инфраструктура

- **Yandex Cloud** как основная площадка (managed PostgreSQL, managed Redis, Object Storage, при росте — managed Kubernetes). Зрелее и документированнее прочих. Альтернативы: VK Cloud, Selectel, Cloud.ru.
- Контейнеры (Docker), деплой — на MVP достаточно одной-двух VM + managed БД; k8s только когда реально понадобится горизонтальное масштабирование.
- CDN для контент-паков и медиа (Yandex CDN).
- CI/CD: GitHub Actions или GitLab CI (сборка Flutter, автотесты, деплой бэка).

## 4. Авторизация: логин + пароль (детально)

Телефона нет. Идентичность — логин (см. развилку ниже) + пароль. Пароль **никогда** не хранится открытым, только хеш.

### Что такое «логин» — развилка восстановления доступа

Это ключевое решение, потому что оно определяет, как восстанавливать доступ (без телефона это неочевидно):

| Вариант | Восстановление | Кому подходит |
|---|---|---|
| **Логин = e-mail** (рекомендую при свободной регистрации) | Self-service: ссылка на почту | Регистрация открытая |
| **Логин = никнейм, аккаунт заводит дилер** | Админ/дилер сбрасывает пароль | B2B через дилер-код |
| Логин = никнейм, без e-mail | Только через админа, иначе аккаунт потерян | Не рекомендую |

Дальше флоу показан для варианта с e-mail; для дилер-провижининга шаг «сброс» заменяется на админ-сброс.

### Флоу

```
Регистрация:
  POST /auth/register  { login, password, device_id }
  Сервер:
   • валидация: длина пароля (длина важнее «спецсимволов»),
     проверка на утёкшие пароли (k-anonymity / HIBP-подобная база)
   • хеш пароля — Argon2id (соль на пользователя, память/итерации по OWASP)
   • создать пользователя (identity = login)
   • НЕ раскрывать, занят ли логин, в общем ответе (антиэнумерация)
   • выдать access JWT (~15 мин) + refresh (ротируемый, отзываемый)

Вход:
  POST /auth/login  { login, password, device_id }
  Сервер:
   • rate-limit (по login + IP + device: N попыток / окно)
   • лок после N неудач, экспоненциальная задержка
   • сверка Argon2id-хеша (constant-time)
   • при успехе — access + refresh, регистрация/обновление device
   • одинаковое сообщение при «нет логина» и «неверный пароль»

Сброс пароля (вариант e-mail):
  POST /auth/reset/request { email }  → всегда 200 (не палим наличие)
     сервер шлёт письмо с одноразовым токеном (TTL 30 мин, один раз)
  POST /auth/reset/confirm { token, new_password }
     сервер валидирует токен, ставит новый хеш, ревокейтит все сессии

Токены на клиенте — в secure storage (Keychain).
  access в заголовке; при 401 — refresh через /auth/refresh.
```

### Безопасность и ПД

- **Пароли:** только Argon2id (или bcrypt как минимум), соль на пользователя, никакого открытого текста и обратимого шифрования. Параметры хеша — по актуальным рекомендациям OWASP.
- **Брутфорс и credential stuffing:** rate-limit на логин/регистрацию/сброс; лок после N неудач; экспоненциальная задержка; капча-челлендж при аномалиях (РФ-совместимая или собственная, не Google reCAPTCHA). Проверка новых паролей по базе утёкших.
- **Антиэнумерация:** не раскрывать, существует ли логин/e-mail — ни при входе, ни при регистрации, ни при сбросе (везде одинаковые ответы/тайминги).
- **Refresh-токены:** хранятся серверно (хэш), привязка к устройству, ротация при каждом обновлении, отзыв. Экран «Мои устройства» → разлогинить сессию. Смена пароля ревокейтит все сессии.
- **ПД:** имя/регион/e-mail — персональные данные → хранение в РФ (152-ФЗ), регистрация оператора ПД, политика конфиденциальности и согласие при регистрации.
- **После регистрации** — экран профиля: имя, регион, (опц.) дилер/организация. Нужно для сертификата и скидок.

### Привязка к дилеру (важно для loyalty-логики)

Пользователь-монтажник может быть привязан к организации/дилеру. Это отдельная сущность (см. модель данных). От неё зависят сертификат и начисление скидок — интеграция с твоим дилерским миром (RRC, каналы). При дилер-провижининге эта же связь даёт и канал восстановления пароля.

## 6. Игровая экономика и почему она server-authoritative

**Ключевой принцип:** всё, что конвертируется в реальную ценность (опыт → дилерская скидка, уровень → статус, сертификат), клиент **не имеет права** начислять сам. Иначе чит = реальные деньги/скидки.

- **Клиент** — только показывает состояние и отправляет события («ответил на вопрос», «прошёл урок»).
- **Сервер** — валидирует и вычисляет XP, тратит/регенерирует жизни, ведёт поток, считает лиги. Источник правды — лог событий; сервер пересчитывает экономику из него.

### Жизни (капли)

Макс. 5, регенерация +1 каждые ~30 мин. **Регенерация считается на лету** из `lives_updated_at` серверным временем — никогда не доверяем часам клиента. Клиент рисует таймер, но списание/восстановление — за сервером.

### Поток (streak)

Инкремент в день, когда пройден ≥1 урок, в таймзоне пользователя. Возможен «предохранитель потока» (streak freeze). Считается сервером по timestamp активности + timezone.

### Опыт и лиги

- XP начисляется сервером при валидированном прохождении. Кривая уровней.
- Лиги — недельные когорты (~30 человек), рейтинг по недельному XP в **Redis ZSET** (ключ = неделя+лига). Повышение/понижение при ротации недели — плановая фоновая задача.

### Анти-чит

- Сервер **пересчитывает XP из лога событий**, не берёт с клиента готовые числа.
- **Практические уроки** можно оценивать на клиенте (мгновенный офлайн-фидбек) — это ок.
- **Сертификационный экзамен** — оценивается **только на сервере и только онлайн**. Значит: ключи правильных ответов экзамена **не должны попадать в клиентский бандл** в открытом виде. Клиент шлёт ответы, сервер грейдит по своему ключу. Это единственный способ сохранить целостность корочки, которая даёт реальную скидку.
- Эвристики аномалий: нереальная скорость, слишком много идеальных прохождений, много устройств на аккаунт. Rate limiting. Подписанные запросы, короткий TTL access-токена.
- Play Integrity в РФ ненадёжен → опираемся на серверные эвристики + механизмы RuStore.

## 7. Офлайн-first и синхронизация

Монтажник часто в поле, связь плохая. Приложение должно играться офлайн.

- **Контент уроков** скачивается заранее (контент-паки) и лежит локально в SQLite → уроки проходятся без сети.
- **События** (ответы, прохождения) складываются в локальную **очередь-outbox** и синкаются, когда появляется сеть.
- **Сервер — источник правды** для экономики. Клиент показывает оптимистичное состояние, сервер сверяет и присылает канон. При расхождении по всему, что связано с ценностью, — прав сервер.
- **Разрешение конфликтов:** экономика — server-authoritative; чисто локальное/косметическое — last-write-wins на клиенте.
- Экзамен — исключение из офлайна: требует онлайна (см. анти-чит).

## 8. Контент-пайплайн и CMS

Уроки — это **данные, а не код**. Иначе каждый новый вопрос = релиз в стор (2 недели модерации). Это смертельно для контентного продукта.

- Единая **JSON-схема** типов заданий: `mc`, `tap-hotspot`, `slider`, `match`, `audio-listen` (послушай насос), `order` и т.д. Клиент — это «движок», умеющий рендерить любой тип из схемы.
- **Веб-CMS** для авторинга: редактор уроков, загрузка медиа/аудио, публикация версий, предпросмотр.
- Клиент скачивает **контент-паки** (юнит = пак) с CDN, кэширует, проверяет версию. Новый контент прилетает без релиза приложения.
- Заложить **версионирование, локализацию и A/B** с самого начала схемы (даже если пока не используешь).

Это ровно то, что мы обсуждали: заменить хардкод прототипа на структуру данных. CMS может быть простой (React-админка или готовый low-code) — не переусложняй на старте.

## 9. Пуш-уведомления

Триггеры: напоминание о потоке, движение в лиге, новый контент, «на объекте небось опять песок хватают» (маскот).

## 12. Фазы (MVP → масштаб)

**Фаза 0 — валидация (сделано частично).**
Прототип есть. Показать 10–20 реальным монтажникам, послушать реакцию. Дёшево, до любого кода.

**Фаза 1 — MVP (2–4 месяца), только iOS.**
- Flutter-приложение (iOS-сборка), движок уроков из JSON.
- Авторизация логин + пароль (Argon2id, сброс через e-mail или админ).
- 1–2 юнита контента, server-authoritative прогресс и XP.
- Жизни, поток. Без лиг, без платежей.
- Сертификат — заглушка (запись + verify-страница).
- TestFlight → App Store бета.

**Фаза 2 — вовлечение (после MVP).**
- Лиги/лидерборды (Redis), пуши (APNs).
- Больше контента, полноценная CMS.
- Задание «послушай насос» (аудио).
- **Интеграция с дилерской скидкой** — тот самый настоящий крючок (опыт/уровень → реальная скидка/статус).

**Фаза 3 — масштаб.**
- ClickHouse-аналитика, закалка анти-чита, A/B.
- Рефералы, устойчивый офлайн.
- `[IAP]` монетизация — только если решишь делать revenue-версию.

## 13. Команда и деньги (ориентир)

Это не соло-проект на выходные. Минимально жизнеспособная команда:

- 1 Flutter-разработчик
- 1 backend-разработчик (может быть частично ты + подрядчик)

Реалистичные пути: (а) собрать MVP скраппи с подрядчиками, (б) нанять маленькую команду, (в) отдать на аутсорс-студию с твоим техлидством. Порядок затрат на MVP сильно зависит от пути — от «своими руками + фрилансеры» до полноценной студийной разработки. Ключ — не строить сразу всё; фазирование снижает риск.

## 14. Главные риски и решения

| Риск | Решение |
|---|---|
| PII россиян за рубежом (152-ФЗ) | Всё PII-хранилище — в российском облаке, регистрация оператора ПД |
| Чит экономики = реальные скидки | Server-authoritative экономика, серверный грейдинг экзамена |
| Каждый вопрос = релиз в стор | Data-driven контент + CMS + контент-паки |
| Забыл пароль → потерял аккаунт | Канал восстановления с самого начала (e-mail или админ-сброс) |
| Брутфорс / credential stuffing | Argon2id, rate-limit, лок, проверка по базе утёкших паролей |
| Слабая связь в поле | Офлайн-first, outbox-синхронизация |
| Преждевременное усложнение | Модульный монолит, не микросервисы; k8s/ClickHouse — по факту боли |
| «Игра ради игры» не взлетит | Реальная ценность за прохождение: сертификат, скидка, статус в дилерке |

## Открытые вопросы (нужно твоё решение)

1. **Регистрация: свободная или через дилер-код?** Это самый срочный вопрос — он определяет и логин (e-mail vs никнейм), и канал восстановления пароля (self-service vs админ-сброс), и модель организаций/скидок. Ответ на него разблокирует детальную проработку auth-модуля.
2. **Loyalty или revenue?** От этого зависит, нужен ли платёжный стек вообще (при iOS-only revenue-версия — это ещё и StoreKit/Apple, отдельная боль для РФ).
3. **Сертификат:** это «внутренняя ачивка Aquario» или заявка на отраслевой стандарт («этот умеет ставить»)? Второе — сильнее, но требует веса бренда и, возможно, партнёрств.
4. **Кто строит:** ты соло с подрядчиками, найм команды или аутсорс-студия? От этого зависит, насколько подробно расписывать каждый модуль.
